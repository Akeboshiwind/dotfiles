# sbx

Docker Sandboxes runs a coding agent in a microVM.
`ct` (a fish function in `cfg/fish`) is the entry point; this directory holds the kit and the template build that make a sandbox look like this machine.

```
kits/osm-base/      the only kit: Claude config and plugins, git identity,
                    GitHub egress, JDK 21, the Clojure toolchain, allium, d2,
                    UTF-8 locale
scripts/            (in the repository root) sbx-build-template.sh,
                    sbx-template-fresh.sh
```

One kit and one template, so every sandbox is the same whatever repository it is working on.
The cost is that what one repository needs, every sandbox carries — JDK 21 is pinned over the image's JDK 25 everywhere, and the Confluent and Quay hosts are reachable from everywhere.
That is the trade the consistency is bought with.

## Kits apply at creation, and nowhere else

A kit is read when a sandbox is **created**.
Nothing in a kit reaches a sandbox that already exists — `sbx kit add` recreates the sandbox rather than modifying it.

The one exception is skills.
`~/.claude/skills` is a live virtiofs mount of a host-side store, so `sbx skills import` (run by `syn`) reaches running sandboxes with no recreate.

So changing a kit is two steps:

1. `syn --apply` — syncs generated files and rebuilds the template if `spec.yaml` changed.
2. Recreate the sandbox — `ct` detects this and offers to do it.

Recreating **discards that sandbox's Claude history**.
The transcripts live on per-sandbox volumes that `sbx rm` deletes; the workspace and the skills store survive.

## Templates cache the installs; the kits stay the definition

`syn` builds the template by creating a throwaway sandbox, letting the kit run, and snapshotting it with `sbx template save`.
`ct` then boots from that template with `-t`.

A template is only ever a cache.
Delete it and sandboxes still come out correct, just slowly, because the kit's install steps run for real instead of finding their work done.
That is the property to preserve when changing anything here.

## Install and startup commands must be idempotent

Every `setup.install` step runs again on top of a template that already contains its work, and every `setup.startup` command replays on each container restart.
A step that only converges the first time breaks both.

Guard on the artefact, not on a record of having installed it:

```yaml
- command: command -v bb >/dev/null || curl -sL .../install | bash
- command: |
    grep -q '^export LANG=' /etc/sandbox-persistent.sh || \
      echo 'export LANG=C.UTF-8' >> /etc/sandbox-persistent.sh
```

A sandbox holding the binary but no bookkeeping is in the desired state and must read as satisfied.

## What a template cannot carry

**Network policy.**
`permissions.network` is sbx policy rather than filesystem, so no snapshot holds it and `ct` passes `--kit` at every create.
Without those flags, egress is default-deny and Clojars, Maven Central and quay.io all fail.

**`files/home/`.**
It is copied from the kit at every create, before any install step.
Whatever a template baked there is never read.

Two consequences that look contradictory and are not:

- **Template freshness ignores `files/`** — `sbx-template-fresh.sh` compares only `spec.yaml` mtimes, so editing `CLAUDE.md` needs no rebuild.
- **`ct`'s staleness check includes `files/`** — a `CLAUDE.md` edit does need a new *sandbox*, because that is when the tree is copied.

**Agent config that sbx rewrites.**
`settings.json` and `~/.claude.json` are recreated at every create.
That is why `kits/osm-base/files/home/.claude/settings.osm.json` exists under a different name and `ct` passes it with `claude --settings`.

## Adding what a project needs

Add it to `kits/osm-base/spec.yaml` — the install step, and any host it has to reach — then `syn --apply` and recreate.

Name the repository in the comment, because the next reader's question is why a universal kit installs something only one build uses.
Neither `manifest.edn` nor `ct` needs an edit.

Every sandbox then carries it, which is the point and also the price: a tool that has to be absent elsewhere, or a version pin that fights another repository, does not belong here and wants a second template instead.

## Generated files

`kits/osm-base/files/home/.claude/` is `cfg/llm/.claude/` minus `settings.json`, generated by `syn` and gitignored.
sbx rejects a symlink under `files/` that resolves outside the kit, so a copy is unavoidable; generating it is what stops it drifting.
Edit `cfg/llm/.claude/`, never the copy.

## Host settings syn cannot own

```bash
$ sbx settings set kit.allowedSources '["docker.io/","github.com/docker/"]'
```

`ct` stacks upstream's `git-ssh-sign` from a pinned git URL, and that source has to be allowlisted once.
It is in no template: it resolves the signing key from the forwarded SSH agent at signing time, so there is nothing to snapshot.
